# Корпоративная информационно-аналитическая система «Учёт клиентов»

Учебный проект по дисциплине «Проектирование корпоративных информационно-аналитических систем».

Веб-приложение для менеджера: ведение единого реестра клиентов компании — карточки с ФИО,
контактами, сведениями об имуществе и комментарием, редактирование карточек и накопительная
история дополнений по каждому клиенту. Хранение — PostgreSQL, запуск полностью локальный на Windows.

---

## 1. Состав системы и стек

| Слой | Технология | Почему здесь |
| --- | --- | --- |
| База данных | **PostgreSQL 17** | реляционная СУБД, внешние ключи, каскадное удаление, транзакционное DDL в миграциях |
| Backend | **Python 3.11+**, **FastAPI**, **SQLAlchemy 2.0 (async)**, **Alembic**, **PyJWT** | асинхронный доступ к БД через `asyncpg`, автоматическая OpenAPI-документация, версиярование схемы |
| Frontend | **React 18**, **TypeScript**, **Vite**, **Ant Design 5**, **TanStack Query 5**, **React Router 6**, **Axios** | корпоративный UI-кит (таблицы, формы, модальные окна), серверное состояние с кэшированием и инвалидацией |
| Авторизация | JWT (Bearer), единственная роль — **менеджер** | вход по логину/паролю на фронтенде, все остальные эндпоинты закрыты |

Как идёт запрос:

```
Браузер (React, http://127.0.0.1:5173)
   │  fetch /api/...          ← прокси Vite, поэтому CORS на разработке не нужен
   ▼
FastAPI (uvicorn, http://127.0.0.1:8000)
   │  проверка Bearer-токена → зависимости FastAPI
   ▼
SQLAlchemy (asyncpg) → PostgreSQL (127.0.0.1:5432, база crm_db)
```

Ролей в системе одна — менеджер. Отдельной таблицы ролей нет: доступ к приложению имеют только
менеджеры, а их перечень заводится администратором через `app.seed`. Роль при этом зашита в поле
`role` JWT, чтобы при добавлении новых ролей не пришлось переизобретать механизм проверки прав.

## 2. Модель данных

Три таблицы (схема создаётся миграцией Alembic):

**`managers`** — учётные записи менеджеров

| Поле | Тип | Примечание |
| --- | --- | --- |
| `id` | SERIAL PK | |
| `login` | VARCHAR(64) UNIQUE | логин для входа |
| `password_hash` | VARCHAR(255) | PBKDF2-HMAC-SHA256, соль индивидуальная, 390 000 итераций |
| `full_name` | VARCHAR(160) | отображается в шапке и в подписи комментариев |
| `is_active` | BOOLEAN | отключённый менеджер не может войти |
| `created_at`, `updated_at` | TIMESTAMPTZ | заполняются сервером |

**`clients`** — карточка клиента

| Поле | Тип | Обязательность |
| --- | --- | --- |
| `id` | SERIAL PK | |
| `last_name` | VARCHAR(120) | обязательно |
| `first_name` | VARCHAR(120) | обязательно |
| `middle_name` | VARCHAR(120) | по желанию |
| `phone` | VARCHAR(64) | по желанию, формат проверяется |
| `email` | VARCHAR(255) | по желанию, валидируется и нормализуется к нижнему регистру |
| `property_info` | TEXT | сведения об имуществе |
| `comment` | TEXT | первичный комментарий к карточке |
| `created_by_id` | FK → `managers.id` (ON DELETE SET NULL) | кто завёл клиента |
| `created_at`, `updated_at` | TIMESTAMPTZ | время последнего изменения видно в списке |

Индексы: `ix_clients_fio (last_name, first_name, middle_name)`, `ix_clients_email (email)`.

**`client_comments`** — история дополнений карточки

| Поле | Тип | Примечание |
| --- | --- | --- |
| `id` | SERIAL PK | |
| `client_id` | FK → `clients.id` ON DELETE CASCADE | удалили карточку — удалилась и её история |
| `author_id` | FK → `managers.id` ON DELETE SET NULL | |
| `author_name` | VARCHAR(160) | снимок ФИО на момент записи: история не «плывёт», если менеджер переименован |
| `text` | TEXT | само дополнение |
| `created_at` | TIMESTAMPTZ | |

Пустые строки из формы backend приводит к `NULL`, поэтому в базе не появляется «мусорных»
пробелов, а поле честно означает «сведений нет».

## 4. Установка с нуля

### 4.1. Что должно быть на машине

* Windows 10/11;
* **Python 3.11 или новее** ([python.org](https://www.python.org/downloads/) — при установке
  включить *Add Python to PATH*);
* **Node.js 18 или новее** ([nodejs.org](https://nodejs.org/));
* доступ в интернет для однократного скачивания переносимого PostgreSQL (~325 МБ) и npm-пакетов.

**Устанавливать PostgreSQL отдельной программой не нужно.** Скрипт скачивает официальную
переносимую сборку EDB, разворачивает её в `.vendor/` внутри проекта и поднимает сервер на
`127.0.0.1:5432`. Права администратора не требуются, системная служба не создаётся,
данные лежат в `.vendor/pgdata`.

### 4.2. Одна команда

Из корня проекта (`D:\work\corporate-crm`):

```bat
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1
```

Скрипт последовательно:

1. проверяет Python и Node.js;
2. создаёт `.env` из `.env.example`, подставляя случайный стойкий `JWT_SECRET`;
3. скачивает и распаковывает PostgreSQL, создаёт кластер, запускает сервер,
   создаёт роль `crm_user` и базы `crm_db` (рабочая) и `crm_test` (для тестов);
4. создаёт виртуальное окружение `backend\.venv` и ставит Python-зависимости;
5. накатывает миграции Alembic;
6. заводит учётную запись менеджера и три демо-карточки клиентов;
7. ставит npm-зависимости фронтенда.

Повторный запуск безопасен: выполненные шаги пропускаются.

### 4.3. Запуск

```bat
scripts\start.cmd
```

Поднимет PostgreSQL (если он ещё не запущен), затем откроет два окна — backend и frontend.
Остановка — закрыть эти окна.

Альтернатива без отдельных окон (оба сервера в одном терминале, остановка по `Ctrl+C`):

```bat
npm run dev
```

### 4.4. Открыть в браузере

| Адрес | Что там |
| --- | --- |
| <http://127.0.0.1:5173> | **само приложение** — вход и реестр клиентов |
| <http://127.0.0.1:8000/docs> | интерактивная документация API (Swagger UI) |
| <http://127.0.0.1:8000/redoc> | та же документация в формате ReDoc |

Учётная запись, созданная установкой:

```
логин:  manager
пароль: manager123
```

## 5. Возможности системы

**Вход.** Форма логин/пароль. Ответы «нет такого логина» и «неверный пароль»
не различаются, чтобы по ответам сервера нельзя было перебирать существующие учётные записи.
Токен хранится в браузере с указанием срока жизни; при истечении или порче токена
система сама выходит на страницу входа.

**Реестр клиентов.** Таблица с ФИО, телефоном, e-mail, сведениями об имуществе, числом
комментариев и датой изменения. Поиск по любому реквизиту: по ФИО (в том числе по двум словам,
«Петров Сер»), по e-mail, по тексту имущества и по телефону — запрос «921 118» найдёт карточку
с телефоном `+7 (921) 118-22-33`, потому что телефон сравнивается по одним цифрам.
Пагинация и подсчёт общего числа записей — на стороне сервера, а не в браузере.

**Карточка клиента.** Создание и редактирование по полям задания. Отправка частичного
набора полей меняет только их, остальные значения сохраняются.

**История дополнений.** На странице клиента можно дописывать комментарии — они образуют
упорядоченную во времени ленту с автором и датой. Карточку можно дополнять, не затирая
прежние записи.

**Удаление.** Карточка удаляется с подтверждением; связанные комментарии уходят каскадно.

## 6. REST API

Все эндпоинты, кроме входа и `health`, требуют заголовок `Authorization: Bearer <токен>`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/auth/login` | вход, выдаёт `{access_token, expires_in, manager}` |
| `GET /api/auth/me` | текущий менеджер |
| `GET /api/health` | состояние API и подключения к БД |
| `GET /api/clients?q=&limit=&offset=` | список с поиском и пагинацией → `{items, total, limit, offset}` |
| `POST /api/clients` | завести клиента |
| `GET /api/clients/{id}` | карточка вместе с историей комментариев |
| `PUT /api/clients/{id}` | редактировать карточку (частичное обновление) |
| `DELETE /api/clients/{id}` | удалить карточку вместе с историей |
| `GET /api/clients/{id}/comments` | только история дополнений |
| `POST /api/clients/{id}/comments` | добавить дополнение |

Пример вручную (PowerShell):

```powershell
$token = (Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/auth/login `
  -ContentType 'application/json' -Body '{"login":"manager","password":"manager123"}').access_token

Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/clients `
  -Headers @{Authorization = "Bearer $token"} -ContentType 'application/json' `
  -Body '{"last_name":"Сидоров","first_name":"Павел","phone":"+7 (903) 555-66-77"}'
```

Ошибки валидации возвращаются в формате FastAPI (`422` со списком `detail`), фронтенд
подсвечивает конкретное поле формы и показывает сообщение по-русски.

## 7. Проверка работоспособности

### 7.1. Тесты backend (25 интеграционных тестов)

Работают с настоящим PostgreSQL в изолированной базе `crm_test`, поэтому рабочие данные
в `crm_db` остаются нетронутыми. Проверяются: вход и отказ входа, отклонение просроченного
и подделанного токена, валидация полей, поиск по всем реквизитам, частичное редактирование,
накопление комментариев, каскадное удаление.

```bat
npm test
```

или напрямую:

```bat
cd backend
.venv\Scripts\python.exe -m pytest -v
```

### 7.2. Сквозная проверка запущенной системы (22 проверки)

Backend и frontend должны работать. Идём через прокси Vite — то есть проверяется та же
цепочка, что и в браузере: прокси → FastAPI → PostgreSQL.

```bat
backend\.venv\Scripts\python.exe scripts\smoke-test.py
```

Создаётся служебная карточка со случайным номером, редактируется, дополняется комментарием
и удаляется — на данных демо она не отражается.

### 7.3. Сборка фронтенда и проверки качества

```bat
npm run build      :: tsc --noEmit + vite build, результат в frontend\dist
npm run typecheck  :: только проверка типов TypeScript
npm run lint       :: ruff по backend (конфигурация — backend\ruff.toml)
```

Правила `ruff` настроены явно, а не «как попало»: отключены `B008` (это сам способ работы
`Depends(...)` в FastAPI) и `RUF001-003` (они принимают кириллицу в комментариях и строках
за подмену латиницы, тогда как проект русскоязычный по условию).

### 7.4. Соответствие схем БД и моделей

```bat
cd backend
.venv\Scripts\python.exe -m alembic check
```

Команда сверяет ORM-модели с реальной схемой PostgreSQL. Ответ `No new upgrade operations
detected.` означает, что миграции и модели не разошлись — удобно проверять перед каждой сдачей.

Все настройки — в файле `.env` в корне проекта (создаётся установщиком из `.env.example`).

| Переменная | По умолчанию | Значение |

## 10. Возможные проблемы

| Симптом | Причина и решение |
| --- | --- |
| «Сервер недоступен» в интерфейсе | не запущен backend. Откройте <http://127.0.0.1:8000/docs>; если не отвечает — запустите `scripts\run-backend.cmd` и посмотрите текст в его окне |
| В окне backend: `PostgreSQL недоступен` | сервер БД не поднят: `powershell -ExecutionPolicy Bypass -File scripts\pg-setup.ps1 -SkipDownload`. Проверьте также, что `DATABASE_URL` в `.env` соответствует созданной роли |
| `initdb` или `pg_ctl` не найден | не распакованы бинарники: уберите `-SkipDownload` у `pg-setup.ps1`, нужен интернет |
| `pip install` ругается на версию Python | нужен Python 3.11+; проверьте `python --version`. Если установлен и Python 2/3 в разных местах, запустите `py -3.12 -m venv .venv` из `backend\` |
| Порт 5432/8000/5173 уже занят | на машине стоит свой PostgreSQL или другой сервис. Смените порт в `scripts\pg-setup.ps1 -Port 5433` и в `DATABASE_URL` в `.env`; порты приложения — `PORT` в `.env` и `server.port` в `frontend\vite.config.ts` |
| Забыт пароль менеджера | `cd backend` → `.venv\Scripts\python.exe -m app.seed --demo --reset` пересоздаст учётную запись из `.env` (данные клиентов при этом будут удалены) |
| Кириллица в `.env` отображается как `???????` | файл пересохранили в кодировке ANSI. `.env` должен быть в UTF-8 (без BOM) — как и `.env.example` |
| После изменений на фронтенде ничего не поменялось | dev-сервер перезапускается сам; проверьте, что окна с `web`/`vite` не закрыты с ошибкой |
| Ошибка 401 сразу после успешного входа | сбились `JWT_SECRET` между запусками (токен подписан старым секретом). Выйдите и войдите заново |

## 11. Ограничения учебного проекта

Осознанные упрощения, о которых стоит знать:

* пароли — PBKDF2-HMAC-SHA256 из стандартной библиотеки (390 000 итераций, индивидуальная соль).
  Для продакшена обычно берут bcrypt/argon2; здесь выбор сделан в пользу отсутствия нативных
  зависимостей и переносимости между машинами;
* токен хранится в `localStorage`, а не в `httpOnly`-cookie: это упрощает разбор механики
  авторизации, но уязвимо к XSS — в реальной системе так делать не стоит;
* PostgreSQL поднимается переносимой сборкой внутри проекта, а не как системная служба: удобно
  для показа и не требует прав администратора;
* нет редактирования состава менеджеров из интерфейса (учётные записи заводит администратор
  через `app.seed`), нет разграничения прав между менеджерами — по условию задания роль одна;
* удаление комментариев и журнал изменений карточки не предусмотрены заданием.
